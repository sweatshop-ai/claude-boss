# 04: The merge gate for deploying branches

**What to build:** a provisional GO (03) or a waived round (05) must never merge into a branch that deploys. Today that would be prose the boss is trusted to follow. This ticket gives the boss one command, `skills/boss/boss_merge.py`, that checks the review record and the repo's own list of non-deploying branches and only then merges, plus a hard rule that closes the boss's other door (a hand-typed `gh pr merge`). The gate fails closed: anything it cannot read counts as a branch that deploys.

**Scope:** rewritten 2026-10-04 after Codex review 1 of the plan (finding 5) and the owner-accepted premortem (R14, R15). This ticket was split on 2026-10-04: the provisional list, the recovery re-review of merged PRs, the post-merge NO-GO and the release stop (R16 to R20) are ticket 06. Why a command and not a hook: `boss-guard.py` warns and never denies (its docstring says so, by design), hooks fire only for registered boss sessions, and `boss-run`'s hard rules see command text, not review state. One command that checks and merges in one step, plus a hard rule against the other door, is testable end to end. It reads the round records of 02 and the `kind` values `codex`, `provisional` (03) and `waived` (05).

**Blocked by:** 03 (Labelled fallback review), 05 (A dead reviewer becomes an open blocker)

**Status:** ready-for-agent

The command:

- [ ] `boss_merge.py --repo OWNER/REPO --pr N [--dry-run] [--test-only-since SHA]` is the one merge path the skill names. `--repo` is required and never inferred; `<owner>` and `<repo>` must match `^[A-Za-z0-9._-]+$` (else exit 2); every `gh` call carries `--repo`. It reads the live PR once with `gh pr view` (head SHA, base branch, state), decides, and only then runs `gh pr merge --repo R N --merge --match-head-commit <the head it read>` (the repo's history uses merge commits; no `--delete-branch`, the skill leaves that to the worker). It needs no checkout: the record is a local file a PR author's push cannot change, and the deploy list comes from the repo through `gh`, so the check cannot be pointed at another repo's files. Exit codes: 0 merged (or allowed, under `--dry-run`, which runs everything except `gh pr merge`), 2 usage, a PR that is not in `--repo`, or a PR that is not open, 3 refused: no GO on the live head (none, a NO-GO, or only an older head), 4 refused: a provisional or waived GO on a branch not listed as non-deploying, 5 `gh pr merge` failed (including a head that moved after the check, which `--match-head-commit` makes `gh` refuse). Every decision appends one line to `pm/reviews/merges.jsonl` in a single `O_APPEND` write (ts, repo, pr, head, base, round, kind, decision, exit, reason, config state, dry-run flag; file mode 0600)

The decision, as a pure function with one test per row (finding 5):

- [ ] The record is the highest-numbered `status: posted` round of this PR whose `head_sha` equals the live head. No such round: refuse (3). Its verdict is `NO-GO`: refuse (3), whatever its kind. Verdict `GO`, kind `codex`: allowed on any base. Verdict `GO`, kind `provisional` or `waived`: allowed only if the base branch is listed non-deploying; otherwise refuse (4). A kind that is none of the three: refuse (4 on a branch not listed non-deploying, 3 on a listed one). Fail closed by construction: every kind other than a Codex GO is refused on a branch that deploys, and 05's `waived` inherits that with its own row in this table. A round whose `status` is `head-moved` or `no-verdict` never counts. Two end-to-end tests feed the gate records made by the real writers, which is why this ticket waits for 03 and 05: a provisional GO made by 03's fallback path (Codex stub absent, `claude` stub GO) and a waived round made by 05's `--waive`, each run with `--dry-run` against a deploying base (exit 4, no `gh pr merge` call) and a listed base (exit 0)

The repo's deploy list (R14):

- [ ] The repo holds `.boss/deploy.json`: `{"version": 1, "non_deploying": ["main"], "test_paths": []}` (`test_paths` optional). It is read from the PR's base branch as committed, with `gh api repos/R/contents/.boss/deploy.json?ref=<base branch>` and never from the PR's head. A branch is non-deploying only if `non_deploying` lists it by exact name (no globs): an allowlist of safe branches, so a new `release` branch deploys by default and a file that names only `main` cannot fail open. Fail closed: the file missing, not JSON, `version` not 1, `non_deploying` not a list of strings, or the `gh api` call failing: every branch counts as deploying, and the log line says which. Tests, one per failure mode, plus a PR whose own head holds a `deploy.json` that lists its base: the verdict does not change, and the `gh` call log shows only the base branch was asked for. This repo gets a `.boss/deploy.json` listing `main` (it has no deploy workflow)
- [ ] The existing test-only exception (fixes after the last GO that touch only tests) is made executable: `--test-only-since SHA` is honoured only when `SHA` is the head of a posted GO round of this PR (and that round passes the decision above for the base) and every file changed between `SHA` and the live head, taken from `gh api repos/R/compare/<SHA>...<head>` with both sides of a rename counted, matches an entry of `test_paths` (`fnmatch` patterns). Without `test_paths`, with any other file, with a compare that fails, or with a page of 300 files (the API's limit), it is refused (3). Tests for each. Without this the gate would silently break the owner's standing rule

The other door (R15):

- [ ] `skills/boss/bin/boss-run` gains a built-in hard rule named `PR merge outside boss_merge` with the pattern `gh[[:space:]]+pr[[:space:]]+merge|pulls/[0-9]+/merge|mergePullRequest`. Tests: `boss-run --dry-run -- gh pr merge 5 --merge` exits 5; so does `gh api -X PUT repos/o/r/pulls/5/merge` and a `gh api graphql` call naming `mergePullRequest`; the `boss_merge.py` command line is not refused; every existing hard-rule test passes unchanged
- [ ] `skills/boss/SKILL.md`: the merge order names `boss_merge.py` and its three outcomes. It states the limit plainly: a `gh pr merge` typed by hand in a worker's or the owner's own shell is outside the gate, the gate stops mistakes and not a determined bypass, and only branch protection on the repo closes that, which the plugin cannot set. It states that a refusal (3 or 4) is an instruction to get the right review, not to work around it. A text test finds the command name and the limit sentence
