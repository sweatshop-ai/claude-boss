# 04: The merge gate for deploying branches

**What to build:** a provisional GO (08) or a waived round (09) must never merge into a branch that deploys. Today that would be prose the boss is trusted to follow. This ticket gives the boss one command, `skills/boss/boss_merge.py`, that checks the review record and the repo's own list of non-deploying branches and only then merges. The gate fails closed: anything it cannot read counts as a branch that deploys. The test-only exception, the hard rule that closes the boss's other door and the skill text are 11.

**Scope:** rewritten 2026-10-04 after Codex review 1 of the plan (finding 5) and the owner-accepted premortem (R7, R14, R25); split on 2026-10-04 (the provisional list and the recheck went to 06 and 10, then the exception, the hard rule and the skill text to 11) and amended after Codex review 3 (findings 10 to 12, 14, 23). Why a command and not a hook: `boss-guard.py` warns and never denies (its docstring says so, by design), hooks fire only for registered boss sessions, and `boss-run`'s hard rules see command text, not review state. One command that checks and merges in one step is testable end to end. It reads the round records of 02 and the `kind` values `codex`, `provisional` (08) and `waived` (09). The filename is historical; the ticket is the gate.

**Blocked by:** 08 (The fallback review, labelled and provisional), 09 (The owner's choice, and the waiver)

**Status:** ready-for-agent

The command:

- [ ] `boss_merge.py --repo OWNER/REPO --pr N [--dry-run]` is the one merge path the skill names. `--repo` is required and never inferred; `<owner>` and `<repo>` match `^[A-Za-z0-9._-]+$` (else exit 2; neither is `.` or `..`), and the record's directory is built from 02's `repo_key(repo)`, never from `--repo` as typed. It reads the live PR once with `gh pr view --repo R N --json number,url,headRefOid,baseRefName,state`, checks identity as 02 does (`number`, URL path), decides, and only then runs `gh pr merge --repo R N --merge --match-head-commit <the head it read>` (the repo's history uses merge commits; no `--delete-branch`, the skill leaves that to the worker). It needs no checkout: the record is a local file a PR author's push cannot change, and the deploy list comes from the repo through `gh`. Every `gh pr` call carries `--repo`; every `gh api` endpoint starts `repos/<owner>/<repo>/` with the validated names; both are asserted from the stub's call log [R7, finding 14]. Exit codes: 0 merged (or allowed, under `--dry-run`, which runs everything except `gh pr merge`), 2 usage, identity mismatch, or a PR that is not open, 3 refused: no usable GO on the live head (none, a NO-GO, or a record that cannot be read), 4 refused: a provisional or waived GO on a branch not listed as non-deploying, 5 `gh pr merge` failed (a head that moved after the check included, which `--match-head-commit` makes `gh` refuse) or the post-merge check below failed, 7 a `gh` read failed. Every decision appends one line to `pm/reviews/merges.jsonl` in a single `O_APPEND` write (ts, repo, pr, head, base, round, kind, decision, exit, reason, config state, dry-run flag; file mode 0600)
- [ ] After `gh pr merge` returns 0 the gate re-reads the PR (`gh pr view --repo R N --json baseRefName,state`). A base other than the one checked, or a PR that cannot be read: exit 5, reason `base-changed` or `unverified`, and `boss-alert 0` (the program from `BOSS_ALERT`, as in 05). Test: the `gh` stub answers base A before the merge and base B after. The claim is this and no more: no `gh` option pins the base (`--match-head-commit` pins only the head), so the gate detects a retarget inside that window after the fact and does not prevent it

The decision, as a pure function with one test per row (findings 5 and 10):

- [ ] The gate walks the PR's `round<NN>.json` files from the highest number down. A file that is unreadable (an empty crash leftover included), not JSON, missing `round`, `head_sha`, `kind`, `verdict` or `status`, whose `round` differs from its file name, whose `status` is `posted` with a null verdict, or whose `kind`, `verdict` or `status` is outside the known values (`codex`, `provisional`, `waived`; `GO`, `NO-GO`, null; `posted`, `head-moved`, `no-verdict`, `post-failed`, `list-failed`) refuses (3, reason `bad-record`) and is never skipped. A valid file whose `head_sha` is not the live head or whose `base` is not the live base (a PR retargeted after the review), or whose `status` is `head-moved`, `no-verdict` or `list-failed`, or `post-failed` with verdict `GO`, is passed over. A valid `post-failed` file on the live head whose verdict is `NO-GO` refuses (3, reason `unposted-no-go`): a NO-GO that could not be posted is still a NO-GO the gate knows, and a later round, numbered higher, supersedes it. The first valid posted round on the live head decides: `NO-GO` refuses (3); `GO` with kind `codex` allows on any base; `GO` with kind `provisional` or `waived` allows only if the base branch is listed non-deploying, else refuse (4). No such round: refuse (3). A bad file below the deciding round is never met, so the next round supersedes a crash leftover. Rows to test: an unreadable newer file, a missing field, an unknown verdict, an unknown kind, an unknown status, a file whose `round` differs from its name, an older GO under a newer NO-GO, a late NO-GO that finished after a GO (so it is numbered higher), `head-moved` and `no-verdict` rounds, a `post-failed` NO-GO (refuses) and a `post-failed` GO (passed over), and a GO on the live head whose `base` differs from the live base (passed over, so refused with 3). Two end-to-end tests feed the gate records made by the real writers, which is why this ticket waits for 08 and 09: a provisional GO made by 08's fallback path (Codex stub absent, `claude` stub GO, `--track` naming a throwaway tracker) and a waived round made by 09's `--waive`, each run with `--dry-run` against a deploying base (exit 4, no `gh pr merge` call) and a listed base (exit 0)

The repo's deploy list (R14, finding 11):

- [ ] The repo holds `.boss/deploy.json`: `{"version": 1, "non_deploying": ["main"], "test_paths": []}` (`test_paths` optional; 11 uses it, matching entries with `fnmatch.fnmatchcase`). It is read from the PR's base branch as committed, with `gh api repos/R/contents/.boss/deploy.json?ref=<base branch>` and never from the PR's head. A branch is non-deploying only if `non_deploying` lists it by exact name (no globs): an allowlist, so a new `release` branch deploys by default and a file that names only `main` cannot fail open. Fail closed: the file missing, not JSON, `version` not 1, `non_deploying` not a list of strings, `test_paths` present and not a list of strings, or the `gh api` call failing: the file is invalid and every branch counts as deploying, and the `merges.jsonl` line's config state says which. Tests, one per failure mode (a string `test_paths` and a mixed list among them), plus a PR whose own head holds a `deploy.json` that lists its base: the verdict does not change, and the `gh` call log shows only the base branch was asked for. This repo gets a `.boss/deploy.json` listing `main` (it has no deploy workflow)
