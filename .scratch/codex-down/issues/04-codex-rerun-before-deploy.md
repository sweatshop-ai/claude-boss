# 04: The merge gate for deploying branches

**What to build:** a provisional GO (08) or a waived round (09c) must never merge into a branch that deploys. Today that would be prose the boss is trusted to follow. This ticket gives the boss one command, `skills/boss/boss_merge.py`, that checks the review record and the repo's own list of non-deploying branches and only then merges. The gate fails closed: anything it cannot read counts as a branch that deploys. The test-only exception, the hard rule that closes the boss's other door and the skill text are 11.

**Scope:** rewritten 2026-10-04 after Codex review 1 of the plan (finding 5) and the owner-accepted premortem (R7, R14, R25); split on 2026-10-04 (the provisional list and the recheck went to 06 and 10, then the exception, the hard rule and the skill text to 11) and amended after Codex review 3 (findings 10 to 12, 14, 23). Why a command and not a hook: `boss-guard.py` warns and never denies (its docstring says so, by design), hooks fire only for registered boss sessions, and `boss-run`'s hard rules see command text, not review state. One command that checks and merges in one step is testable end to end. It reads the round records of 02 and the `kind` values `codex`, `provisional` (08) and `waived` (09c). The filename is historical; the ticket is the gate. The command:

- [x] `boss_merge.py --repo OWNER/REPO --pr N [--dry-run]` is the one merge path the skill names. `--repo` is required and never inferred; `<owner>` and `<repo>` match `^[A-Za-z0-9._-]+$` (else exit 2; neither is `.` or `..`), and the record's directory is built from 02's `repo_key(repo)`, never from `--repo` as typed. It reads the live PR once with `gh pr view --repo R N --json number,url,headRefOid,baseRefName,state`, checks identity as 02 does (`number`, URL path), decides, and only then runs `gh pr merge --repo R N --merge --match-head-commit <the head it read>` (the repo's history uses merge commits; no `--delete-branch`, the skill leaves that to the worker). It needs no checkout: the record is a local file a PR author's push cannot change, and the deploy list comes from the repo through `gh`. Every `gh pr` call carries `--repo`; every `gh api` endpoint starts `repos/<owner>/<repo>/` with the validated names; both are asserted from the stub's call log [R7, finding 14]. Exit codes: 0 merged (or allowed, under `--dry-run`, which runs everything except `gh pr merge`), 2 usage, identity mismatch, or a PR that is not open, 3 refused: no usable GO on the live head (none, a NO-GO, a record that cannot be read, or a provisional or waived GO that a later round supersedes, reason `superseded-go`), 4 refused: a provisional or waived GO on a branch not listed as non-deploying, 5 `gh pr merge` failed (a head that moved after the check included, which `--match-head-commit` makes `gh` refuse) or the post-merge check below failed, 7 a `gh` read failed, or the PR's lock could not be taken (reason `lock-failed`). The gate holds the PR's lock (02's `open_lock`, the one a review takes to claim a round) from its read of the rounds to the return of `gh pr merge`, so a round claimed meanwhile cannot be missed (added after Codex round 1 of the build). Every decision appends one line to `pm/reviews/merges.jsonl` in a single `O_APPEND` write (ts, repo, pr, head, base, round, kind, decision, exit, reason, config state, dry-run flag; file mode 0600); a merge writes a `merging` line (exit null) before it runs `gh pr merge`, so a crash after GitHub accepted the merge leaves a trace, and if that line cannot be written nothing is merged (exit 5, reason `log-failed`)
- [x] After `gh pr merge` returns 0 the gate re-reads the PR (`gh pr view --repo R N --json baseRefName,state`). A `state` other than `MERGED` (`gh pr merge` can return 0 and leave the PR open or queued, so exit 0 needs `state == "MERGED"`), a base other than the one checked, or a PR that cannot be read: exit 5, reason `not-merged`, `base-changed` or `unverified`, and `boss-alert 0` (the program `codex_blocker.default_alert()` names, `codex_blocker.py:80`: `BOSS_ALERT` or the plugin's `bin/boss-alert`; one `subprocess.run([alert, "0", text], timeout=20)`, a failure of it said on stderr and never changing the exit code, as `codex_blocker._post` does at :271). Tests: the `gh` stub answers base A before the merge and base B after; the stub answers state `OPEN` after a `gh pr merge` that returned 0, which gives exit 5, reason `not-merged`, and one alert. The claim is this and no more: no `gh` option pins the base (`--match-head-commit` pins only the head), so the gate detects a retarget inside that window after the fact and does not prevent it

The decision, as a pure function with one test per row (findings 5 and 10):

- [x] The decision is one pure function, `decide(rounds, head, base, non_deploying)`, with `head` and `base` as arguments (11 calls it with the head of an earlier GO). The gate walks the PR's `round<NN>.json` files from the highest number down. A file that is unreadable (an empty crash leftover included), not JSON, missing any of the eight fields the walk reads (`repo`, `pr`, `round`, `head_sha`, `base`, `kind`, `verdict`, `status`), whose `round` or `pr` is not an exact integer (a string, a float or a bool is not one), whose `round` differs from its file name, whose `repo` is not `repo_key(--repo)` or whose `pr` is not the PR's (the same test `_codex_rounds` makes, `boss_review.py:1120`, ownership check at :1146), whose JSON makes the parser itself raise (nested deep enough to raise `RecursionError`: ticket 25 found it in the prune, class c; a file name of over 4300 digits, where `int()` raises `ValueError`, cannot be created on the target filesystems, as ticket 25 records, so the name parser is tested directly with a synthetic string and never with a file on disk), whose `status` is `posted` or `post-failed` with a null verdict (the writer never makes the second; the build refuses it too, fail closed), or whose file is not a regular file, or is one of two files for one round number (`round1.json` and `round01.json`; neither is read), or whose `kind`, `verdict` or `status` is outside the known values (`codex`, `provisional`, `waived`; `GO`, `NO-GO`, null; `posted`, `head-moved`, `no-verdict`, `post-failed`, `list-failed`) refuses (3, reason `bad-record`) and is never skipped. A valid file whose `head_sha` is not the live head or whose `base` is not the live base (a PR retargeted after the review), or whose `status` is `head-moved`, `no-verdict` or `list-failed`, or `post-failed` with verdict `GO`, is passed over. A valid `post-failed` file on the live head whose verdict is `NO-GO` refuses (3, reason `unposted-no-go`): a NO-GO that could not be posted is still a NO-GO the gate knows, and a later round, numbered higher, supersedes it. The first valid posted round on the live head decides: `NO-GO` refuses (3); `GO` with kind `codex` allows on any base; `GO` with kind `provisional` or `waived` allows only if the base branch is listed non-deploying, else refuse (4). No such round: refuse (3). A bad file below the deciding round is never met, so the next round supersedes a crash leftover. Rows to test: an unreadable newer file, a missing field, an unknown verdict, an unknown kind, an unknown status, a file missing `repo`, one missing `pr`, one missing `base`, a `round` or `pr` that is a string or a bool, a file whose `round` differs from its name, an older GO under a newer NO-GO, a late NO-GO that finished after a GO (so it is numbered higher), `head-moved` and `no-verdict` rounds, a `post-failed` NO-GO (refuses) and a `post-failed` GO (passed over), a GO on the live head whose `base` differs from the live base (passed over, so refused with 3), a deeply nested JSON file (refused with 3, reason `bad-record`, no traceback) and the name parser called with a 4301-digit string (it raises nothing and the name counts as a bad record). Two end-to-end tests feed the gate records made by the real writers, which is why this ticket waits for 08 and 09c: a provisional GO written by an in-process `review(..., allow_fallback=True, track=<a throwaway tracker>)` call (Codex stub absent, `claude` stub GO; both arguments are given, so the test holds whether or not 06 has landed) and a waived round made by 09c's `--waive`, each run with `--dry-run` against a deploying base (exit 4, no `gh pr merge` call) and a listed base (exit 0)

- [x] A provisional or waived GO decides only while it is the PR's highest-numbered round file of any status (`posted`, `post-failed`, `head-moved`, `no-verdict`, `list-failed`) (added by 22, 2026-11-12, case A of 22). Any later round, whatever its head or status, means that GO no longer decides and the PR needs a new round: the gate refuses (3, reason `superseded-go`). This covers a later `post-failed` provisional GO, which replaced the PR's entry in 06a's list (06a replaces the entry before posting and keeps it when posting fails), and a Codex GO on another head that removed the entry by 06b's rule 2. Test: a provisional GO on head A posted (round 1), a provisional GO on head B `post-failed` (round 2), a force-push back to A: the gate refuses. A second test: a provisional GO on A (round 1), a Codex GO on B (round 2), a force-push back to A: the gate refuses and no `gh pr merge` call is logged. A `codex` GO on the live head is not bound by this box's base rule: it decides on any base, as above. But the walk goes from the highest round down and stops at the first deciding one, so a Codex GO (round 1) with a provisional GO (round 2) on the live head and any round 3 reaches round 2 first and refuses with `superseded-go`, never meeting the Codex GO. That fail-closed precedence is intended (a later provisional or waived round means the PR was judged again by something weaker and needs a new round), and it has a test row. 11's call with the head of an earlier GO is the same function and follows the same decision. For a provisional or waived GO this box overrides the walk's "passed over" for later `head-moved`, `no-verdict` and `list-failed` rounds: they do not decide, but they do supersede (a test row each). So does any other valid round that was passed over: one on another base (a retarget) and a `post-failed` GO on the same head (a test row each, added by 27)

The repo's deploy list (R14, finding 11):

- [x] The repo holds `.boss/deploy.json`: `{"version": 1, "non_deploying": ["main"], "test_paths": []}` (`test_paths` optional; 11 uses it, matching entries with `fnmatch.fnmatchcase`). It is read from the PR's base branch as committed, with `gh api repos/R/contents/.boss/deploy.json?ref=<base branch>` (the branch name percent-encoded, so `release/1.0` is one value; the answer's `content` is base64, decoded before the JSON is read; a `content` that is absent or a directory listing counts as an invalid file; the base64 is decoded strictly, after the line breaks GitHub puts in it are dropped, and any other character outside the alphabet makes the file invalid, since a lenient decoder would read a corrupted answer as the file it was) and never from the PR's head. A branch is non-deploying only if `non_deploying` lists it by exact name (no globs): an allowlist, so a new `release` branch deploys by default and a file that names only `main` cannot fail open. Fail closed: the file missing, not JSON, `version` not 1, `non_deploying` not a list of strings, `test_paths` present and not a list of strings, or the `gh api` call failing: the file is invalid and every branch counts as deploying, and the `merges.jsonl` line's config state says which: `ok`, `missing` (the `gh api` call answered 404), `unreadable` (it failed or ran past the timeout), `bad-content`, `not-json`, `bad-version`, `bad-non-deploying` or `bad-test-paths`. Tests, one per failure mode (a string `test_paths` and a mixed list among them), plus a PR whose own head holds a `deploy.json` that lists its base: the verdict does not change, and the `gh` call log shows only the base branch was asked for. This repo gets a `.boss/deploy.json` listing `main` (it has no deploy workflow: `.github/workflows/` holds `tests.yml` only; the file does not exist on `main` yet)
