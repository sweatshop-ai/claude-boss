# 03: The fallback reviewer is confined to read-only

**What to build:** when Codex is not there, the PR gate falls back to Claude Opus in read-only mode (decided by the owner 2026-10-03; do not reopen: only `codex` and `claude` are installed, so the fallback is the same family as the Claude workers, and the label, the recovery re-review of 10 and the gate of 04 make up for that). This ticket builds and tests the confinement and nothing else: the exact `claude` call with its flags, the additive `extra_args` on 01's `Fallback`, `boss_review.py --check-fallback`, and the timeout bound. It does not yet run the fallback from `review()`; 08 does.

**Scope:** amended 2026-10-04 after Codex review 1 of the plan (finding 3) and the owner-accepted premortem (R3 in part, R13, R25), and split on 2026-10-04 after Codex review 3 (findings 1, 17, 23): this is the confinement half of the original 03; the review integration is 08. The fallback stays inside the one code path of 02 and 07: same brief, same fence, same findings format, same redaction. Amended again on 2026-10-04 after Codex review 1 of this ticket (`plan-review-codex-03-1.md`): one argv builder shared by the real call and the check, `extra_args` ahead of `-p`, a command-line transport for `extra_args` (the chain runs as a child process, so a `Fallback` object cannot cross it), a fail-closed contract for the check, and an honest timing bound.

Fallback spec ("read-only" named and tested, R13):

- [ ] The fallback is the `claude` call `claude --tools "Read,Grep,Glob" --strict-mcp-config --disable-slash-commands --permission-mode dontAsk -p --model claude-opus-5-5 <prompt>`. One function builds every fallback `claude` argv, `reviewer_chain.claude_argv(fallback, prompt)`, and `_claude` and the check both call it: `claude`, then `--allowedTools <csv>` when `allowed_tools` is set, then the `extra_args`, then `-p --model <model> <prompt>`. The extras go **ahead of `-p`** because `--tools`, `--allowedTools` and `--mcp-config` take a variable number of values and `-p` ends them, so no `extra_args` can swallow the prompt as one more tool name (checked 2026-10-04 with `claude` 2.1.289, run with an empty config directory and no credentials so that no model call is made: `claude -p --tools Read ok` fails with "Input must be provided either through stdin or as a prompt argument"; `claude --tools Read -p ok` and `claude -p --tools Read -- ok` get as far as the login check). `Fallback` refuses an `extra_args` that is not a tuple of strings, or that holds a bare `--` (it would end option parsing before `-p`). The model id and each flag value are `policy.py` constants (`REVIEW_FALLBACK_MODEL`, `REVIEW_FALLBACK_TOOLS`, `REVIEW_FALLBACK_PERMISSION_MODE`). The working directory: `_claude` and `run_chain` inherit it; 02's `_ask_codex` starts the chain in a child process whose directory is the checkout, 08 keeps that and tests the directory its `claude` stub records (08's own box); this ticket sets a working directory only for the check below. Why these flags, checked 2026-10-04 with `claude` 2.1.288 and again with 2.1.289: `--tools` restricts the built-in tool set (its init event listed exactly `Glob`, `Grep`, `Read`); without `--strict-mcp-config` the same `--tools` value still left 511 tools in the init event, 508 of them MCP tools (mail drafts and file-store writes among them); `--allowedTools` only pre-approves tools and removes none, so it is not the mechanism
- [ ] 01's `Fallback` carries `allowed_tools`, which becomes `--allowedTools`; 03 leaves it `None`. This ticket adds `extra_args: tuple[str, ...] = ()` to `Fallback` in `reviewer_chain.py` itself, additively (the default, empty, changes nothing for `boss-run`); a test shows `Fallback` without it still produces today's argv, `claude -p --model <model> <prompt>`. The boss decided on 2026-10-04 that 03 owns this change and 01 does not define the field. A function `boss_review.fallback_spec(timeout=REVIEW_FALLBACK_TIMEOUT)` returns `Fallback("opus", REVIEW_FALLBACK_MODEL, timeout=timeout, when=("absent", "timeout", "error"), extra_args=(...))`; 08 passes it to the chain
- [ ] `extra_args` crosses the chain's command line, because `_ask_codex` starts the chain as a child process and a `Fallback` object cannot cross that boundary: `reviewer_chain.py` gains `--fallback-extra-args JSON` (one argument, a JSON list of strings; like the other `--fallback-*` options it needs `--fallback-name` and `--fallback-model`, and a value that is not a list of strings is a usage error, exit 2), and a function `reviewer_chain.fallback_flags(fallback)` that renders every field of a `Fallback` as the flags that rebuild it, so 08 serializes the whole spec and cannot drop the confinement flags. Tests: a `Fallback` with every field set is rebuilt equal from `fallback_flags` by the command-line parser; and `fallback_flags(fallback_spec())` given to the chain's command line makes the `claude` stub receive exactly `claude_argv(fallback_spec(), prompt)`
- [ ] The `claude` stub records its argv. A test asserts the whole argv of the real fallback call as one list (`claude_argv` agrees with it), so each flag and value above, the order, and the prompt as the last element are all pinned; that the `--tools` value is exactly `Read,Grep,Glob`; that `--model` is the policy constant; that `--dangerously-skip-permissions`, `--allowedTools`, `--allowed-tools`, `--bare`, any `--mcp-config` and any `--permission-mode` other than `dontAsk` are absent; that with `extra_args=("--tools", "Read")` the argv still ends `-p --model <model> <prompt>` (the prompt is not swallowed); that `Fallback(extra_args=("--",))` and an `extra_args` that is not a tuple of strings are refused; and, with `allowed_tools` set too, the order `--allowedTools`, the extras, `-p`

The check (finding 1):

- [ ] `boss_review.py --check-fallback --checkout DIR` runs the fallback call in stream-json mode with a one-word prompt, from the working directory `DIR`. It is a mode of its own: `--checkout` is required and must be a directory, and `--repo`, `--pr` and `--author` are refused there (exit 2, nothing run), as the review's usage errors are; `--checkout` stays required, never inferred from the current directory, as 02 never infers `--repo`. The call is built by `claude_argv` from `fallback_spec()` with `--output-format stream-json --verbose` added (`claude -p` refuses stream-json without `--verbose`, checked 2026-10-04: "When using --print, --output-format=stream-json requires --verbose"), so the diagnostic argv equals the real one but for those three tokens, and a test asserts that. It runs under 01's process handling (`_spawn`) with the spec's timeout. Exit 0 only if `claude` exited 0 and the output passes the fail-closed contract; otherwise 1, with each reason on stderr; exit 2 is for usage only. The contract: stdout is read as newline-delimited JSON, each non-blank line a JSON object; exactly one `{"type": "system", "subtype": "init"}` event; its `tools` a list of exactly the three distinct strings `Glob`, `Grep`, `Read` (any order); its `mcp_servers` present and an empty list; its `model` a string exactly equal to `REVIEW_FALLBACK_MODEL` (no suffix, no prefix match). The decision is a function over the parsed events and is tested with a `claude` stub that prints recorded stream-JSON fixtures: one pass, and one fail each for an extra tool, an MCP server, a wrong model, a model with a suffix, a missing tool, a duplicated tool, a missing `mcp_servers` key, `tools` or `mcp_servers` of the wrong type, no init event, two init events, a line that is not JSON, a non-zero exit after a good init, a timeout (the stub hangs; the test passes a timeout of 1 second) and a `claude` that is not on `PATH`. A test asserts the stub's recorded working directory is `DIR`. The suite never calls the real `claude`. The author runs the real check once as a manual smoke test and pastes its output in the PR; it is not a pass condition

Timeouts (R3 in part, finding 17):

- [ ] Codex and the fallback have separate timeout constants in `policy.py` (`REVIEW_CODEX_TIMEOUT` is 02's, `REVIEW_FALLBACK_TIMEOUT` is added there by 02 and used here), both 600 seconds in production. An elapsed-time test runs 01's chain with `fallback_spec(timeout=1)` and `codex_timeout=1` against a Codex stub that hangs and ignores SIGTERM (so it is stopped by the KILL that follows `TERM_GRACE`) and a `claude` stub that answers: the Codex attempt is logged `timeout`, the fallback answers, and the total elapsed time is at least the Codex timeout and under `codex_timeout + fallback_timeout + TERM_GRACE + 5` seconds, the 5 covering interpreter and stub start-up and scheduler variance (stated in the test). The bound is stated, not removed: a hung Codex costs one timeout per review, an absent or failing Codex costs nothing. The chain runs as a child process under 02's `_ask_codex`, whose own deadline is `codex_timeout + REVIEW_CHAIN_SLACK`; the longer deadline that the fallback needs there is 08's change and 08's test, through `_ask_codex` itself

Tests:

- [ ] Tests use 01's stub-directory harness with its PATH guard (a logging stub for each of `codex`, `claude` and `gh`, the `gh` log empty here; a temp `HOME` and `CLAUDE_CONFIG_DIR`; `BOSS_TYPESAFE_ENV` pointing at a missing file): each test asserts its stub call logs and fails if `codex`, `claude` or `gh` resolves outside the stub directory [R25]. Cases: the argv assertions, `Fallback` without `extra_args` unchanged, the command-line transport, the `--check-fallback` fixtures and its usage errors, and the elapsed-time test
