# 05: A dead reviewer becomes an open blocker

**What to build:** after N failed Codex attempts in a row (N in the policy module), the boss's tracker gets an open blocker "Codex down" with a ladder marker. It escalates on the normal rungs without a boss turn and reaches the owner once through `AskUserQuestion`, with three options: wait, accept the fallback review, or merge on tests alone (never on a branch that deploys). It clears after M answered Codex attempts in a row. Today an outage leaves every PR waiting with nothing telling the boss what to do; this makes it an open blocker the ladder already knows how to raise.

**Scope:** amended 2026-10-04 after Codex review 1 of the plan (finding 7) and the owner-accepted premortem (R21 to R24, R25). Blocked by 03 as well as 02 because the owner's option "accept the fallback review" does not exist before 03. Health is judged from real review attempts only: there is no synthetic Codex probe, so a recovered Codex is noticed at the next review or at 06's recheck pass, and the blocker stays open until then.

**Blocked by:** 02 (PR review becomes a command), 03 (Labelled fallback review)

**Status:** ready-for-agent

All repos count together, because there is one Codex per config dir, and an answered attempt anywhere ends a failure streak (R21). Torn or malformed lines are skipped and counted in the result. Table tests: F,F,F is down; F,F,ok,F is not down; F,F,F each followed by a fallback answer is down; down then ok,F,ok is still down; down then ok,ok is up; a `noverdict` between failures changes nothing; two separate processes each appending one failure reach N

Raising the blocker (R23, R24):

- [ ] `boss_review.py --track T` (the track from the dispatch header) runs `codex_health` after it has logged its attempts; `T` must match `^[a-z0-9][a-z0-9._-]{0,63}$` and its tracker must be a regular file under `pm/`; without `--track`, or without that file, stderr says no blocker can be raised and the review result is unchanged. When the state is down and no `Codex down` blocker is open, one line is added inside one `tracker.update`: `- Codex down: N failed Codex attempts in a row (last: <repo>#<pr> <reason>; K PRs affected) - T+0 <ts> [ladder id=cd<yymmddHHMM> t0=<ts> last=0 next=<t0 + 5 min> ask="<the action>"]`, built with `tracker.render_marker`, then `boss-alert 0` (the program from env `BOSS_ALERT`, default `skills/boss/bin/boss-alert`; the ladder never posts rung 0). "Open" means a line under the first `## Open blockers` whose marker id matches `cd` plus ten digits and has no `cleared=`; the check and the add are in the same locked update, so eight concurrent processes at the Nth failure give one blocker. A new outage after a cleared one gets a new id, because a cleared marker is skipped by the ladder for good. The `ask=` text names the action: the owner chooses wait, accept the fallback review, or merge on tests alone. A failed `boss-alert` is reported on stderr, not retried, and the ladder's rung 5 still follows
- [ ] After the write a test runs `tracker.scan_marker` and `tracker.validate` on the new line and asserts its index lies inside `tracker.blockers_range` (R24).
