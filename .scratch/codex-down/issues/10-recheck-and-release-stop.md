# 10: Codex re-reviews every provisional GO, and a release waits for it

**What to build:** when Codex answers again, each PR on 06a's provisional list gets a Codex review on its live head (an open PR) or its merged head (a merged PR, reviewed in a detached worktree); a PR closed without a merge gets none. A Codex NO-GO on a merged PR becomes an open blocker on the ladder and a dispatched fix. A release or wrap-up stops while the list holds an entry that counts (the entry of a PR closed without a merge does not). Recovery is Codex-only: a re-review never falls back to Claude.

The recheck (R17, R18):

- [ ] `skills/boss/boss_recheck.py --track T --repo OWNER/REPO --checkout DIR [--author NAME]` (`--author` defaults to `recheck` and matches 02's name rule) takes the entries of that repo (`provisional_entries` of the tracker `codex_blocker.usable_tracker(T)` returns, matched by 02's `repo_key`; an unusable track is exit 2) one at a time with no entry able to stop or erase another, calls `prune_provisional` at the start of the pass and after each review, and for each entry calls `review(...)` with `allow_fallback=False` and `track=T` (so 05c's health sync runs): a merged PR with `head_sha=<its merged headRefOid>` (not the entry's `head=`, see the merged-head box below), a PR that is `CLOSED` without a merge not at all, an open PR without `head_sha`, so it is reviewed on its live head. The review always runs in a detached temporary worktree outside `--checkout` (`git fetch origin refs/pull/<N>/head`, which GitHub keeps for open, merged and closed PRs, the branch being gone or advanced after a merge, then `git worktree add --detach` at the SHA `_live_state` read, `FETCH_HEAD` and HEAD verified equal to it, removed afterwards even when the review fails, leftovers pruned at the start of a pass), so a deleted or advanced branch cannot change what is reviewed and the shared checkout is never moved. Outcomes: a Codex GO leaves the entry to `prune_provisional`; a Codex NO-GO (`result.verdict` `NO-GO` with `status` `posted` or `post-failed`: an unposted NO-GO is still a NO-GO, as 04's `unposted-no-go` says) on an open PR leaves the entry and prints `NO-GO <repo>#<N> round <NN> author=<name>` for the boss to dispatch (`<name>` is the `author` of the entry's own round); no Codex answer (any other exit of `review()`: 4, 6, 7, a `head-moved`, `no-verdict` or `list-failed` status, a round left empty), a fetch that fails, or a `gh pr view` that fails (`_live_state` gives None) leaves the entry and goes on to the next one; the entry then still counts for `--list`. A leftover round file that `prune_provisional` cannot read keeps its PR's entry for good (ticket 25, second box, decides who clears it; this ticket does not)
- [ ] A Codex NO-GO on a merged PR (R20) writes an open blocker first, then removes the entry itself (the one case where a NO-GO removes an entry). The blocker is one line under the first `## Open blockers`: `- Codex NO-GO on merged <repo>#<N> (round <NN>) - T+0 <ts> [ladder id=fx<8 hex of sha1 of "<repo>#<N> round <NN>"> t0=<ts> last=0 next=<t0 + 5 min> ask="<action>"]` (`tracker.render_marker(id_, t0, nxt, ask=...)`, `tracker.py:202`; `policy.RUNGS[0]` is the 5 minutes; the id is `fx` and 8 hex digits, which `tracker.ID_RE` takes), `<NN>` being the number of the NO-GO round just claimed. **The id is per round, not per PR (ticket 16, finding 4, decided here):** `tracker.add_line` skips a line whose tag is anywhere in the file, a cleared line included, so an id made from the PR alone would lose the alert of a second NO-GO on the same PR after the first blocker was cleared; with the round in the id a second NO-GO is a new round and a new id, while a retry of the same round finds its own line and adds nothing. It is written with 05a's `tracker.add_line(path, tracker.BLOCKERS, line, tracker.marker_tag(id_), deadline)`, and `boss-alert 0` is called once, only when `add_line` answers `done` (not `done (already there)`), through `codex_blocker.default_alert()`. `<action>` names the PR and the round's `.out` file under `pm/reviews/<repo_key>/pr<N>/` (`round<NN>.out`, beside the record `ReviewResult.record`) and says to dispatch its author or any free worker. The recheck prints `DISPATCH <repo>#<N> author=<name> round=<NN>`, `<name>` being the `author` of the entry's own round. **Crash and resume:** the blocker is written before the entry is removed, so a crash between the two leaves the entry. Before it reviews a merged entry, the recheck looks at the highest posted `kind: codex` round on the merged head that is numbered above the entry's `round=`: if that round is a NO-GO, it does not review again, it adds the blocker for that round (a no-op when it is there) and removes the entry. So the next pass neither adds a second blocker nor claims a new round. The blocker is the guaranteed minimum: the ladder raises it with no boss turn even when no author session exists, and it stays open until the fix has merged on a Codex GO, then the boss sets `cleared=` and posts `boss-alert clear`

- [ ] A merged PR is reviewed at its merged `headRefOid`, not at the entry's `head=` (added by 22, 2026-11-12, case B of 22): a provisional GO on A, then on B (the entry now names B), the PR goes back to A and merges (a merge outside `boss_merge.py`, which 04's `superseded-go` refuses). A Codex GO on the merged head removes the entry by 06b's rule 4 (built and tested in 06b); a Codex NO-GO writes the post-merge blocker above and then removes the entry; a failed or stalled review leaves the entry and the release stop holds. The recheck does not review a PR that is `CLOSED` without a merge (06b's rule 3 keeps its entry), and `--list` does not count the entry of a closed PR; a PR whose state cannot be read counts (it is not known to be closed).
