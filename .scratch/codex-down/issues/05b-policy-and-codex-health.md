What counts, and the numbers (finding 7, R21, R22):

- [ ] `policy.py` gains `CODEX_DOWN_AFTER = 3` (failed Codex attempts in a row) and `CODEX_UP_AFTER = 2` (answered Codex attempts in a row, so one answer amid failures never clears: R22), each with a comment in the file's style (what it counts, the date, the owner's reason), and the module docstring's list of what lives there gains "Codex health". `skills/boss/SKILL.md` quotes both in the Codex paragraph (the one that starts "Codex is the external reviewer, twice"), and `test_policy.py`'s `QUOTES["skills/boss/SKILL.md"]` gains one quote of each built from the constants. Why 2: it is the smallest value that satisfies R22, and 10's recheck passes supply the second answer quickly; a larger value would leave a recovered outage on the ladder for hours
- [ ] `skills/boss/codex_health.py` derives the state from `pm/reviews/attempts.jsonl` (under `$CLAUDE_CONFIG_DIR`, `boss_store.pm_dir() / "reviews" / "attempts.jsonl"`, the file `boss_review.append_attempts` writes, one O_APPEND write per run) in one scan in file order and stores no counter. A line is `{"ts", "repo", "pr", "round", "reviewer", "reason", "exit_code"}`. It reads Codex attempts only (`reviewer` `codex`; the fallback's lines, `opus` or whatever 03's spec names it, are ignored and not counted as skipped): `absent`, `timeout` and `error` are failures, `answered` is a success, `noverdict` counts as neither (Codex answered without a usable verdict, which is neither proof of an outage nor of health; with 08's `when=("absent", "timeout", "error")` the fallback does not run on it either). A Codex attempt that gave a usable verdict is `answered` even after a non-zero exit, by 01's precedence rule. A fallback answering does not turn the Codex attempt before it into a success (finding 7). All repos count together, because there is one Codex per config dir, and an answered attempt anywhere ends a failure streak (R21). **The `round` field is never read** (2026-11-12, ticket 13): an attempt whose answer was refused after the chain ran (a NUL in it) is logged with `"round": null`, exit 7, and is still a real Codex attempt with a `reviewer` and a `reason`, so it counts by those two like any other (a refused `answered` is a success: Codex did answer; the refusal is the review's, not Codex's); a line with `round` absent, null or any value counts the same. The streak rules: `answered` adds 1 to `answers` and sets `failures` to 0; a failure adds 1 to `failures` and sets `answers` to 0; `noverdict` changes nothing; the state starts `up`, becomes `down` when `failures` reaches `policy.CODEX_DOWN_AFTER`, and from `down` becomes `up` when `answers` reaches `policy.CODEX_UP_AFTER`. A line that is not a JSON object, is torn (no closing newline, or not parseable), or whose `reviewer` or `reason` is missing, not a string, or (for `codex`) outside the closed set `absent|timeout|error|noverdict|answered` is skipped and counted; a missing file is `up` with zeros. The function `health(path)` returns the state, `failures`, `answers`, `skipped`, and for 05c's blocker text the last failure's `repo`, `pr` and `reason` and the number of distinct `repo#pr` among the failures of the current streak. `python3 skills/boss/codex_health.py` prints one JSON line `{"state": "down"|"up", "failures": n, "answers": n, "skipped": n}` and exits 0 (the blocker text's extras are not in that line). Table tests: F,F,F is down; F,F,ok,F is not down; F,F,F each followed by a fallback answer is down; down then ok,F,ok is still down; down then ok,ok is up; a `noverdict` between failures changes nothing; a torn line is skipped; a refused-answer line (`round` null, `answered`) between two failures is an answer, and a refused-answer line (`round` null, `timeout`) is a failure; a line with `round` absent is counted; two separate processes each appending one failure through `boss_review.append_attempts` reach N
