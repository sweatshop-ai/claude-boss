# 09a: A hand clear holds until a later failure is logged

**What to build:** a `Codex down` blocker the owner closed by hand (typed `cleared=<time>` on its line) must not come back at the next `--track` review while nothing new has failed. This is class b of 20, decided here (Astrid, 2026-11-12, after Codex spec round 1, finding 4; Chiara ruled the wording right).

**Scope:** split out of 09. Today `codex_blocker.sync` raises whenever the state is down with `failures >= CODEX_DOWN_AFTER` and no `cd` line is open, so a hand-cleared blocker returns after a `noverdict`, or a run that logged nothing, and 09b's choice, bound to the old id, would be asked again for the new one. A failure count marker was considered and dropped: a hand clear has no count to record. Timestamps are the approximation: `attempts.jsonl` is ordered by file position, not by `ts` (`codex_health.py:67`, pinned by `test_codex_health.py:92`), so a writer that appended a failure whose `ts` was taken before the clear can be read as old; that case is accepted and documented, not solved.

**Blocked by:** 05c (merged). 09b's SKILL sentence about `cleared=` promises this ticket's hold, so 09a lands first.

**Status:** ready-for-agent

- [ ] `codex_health.health()` also returns `last_ts`: the `ts` of the newest failure of the current streak (the last `FAILURES` line in file order), a timezone-aware `datetime`, or None when the line has no parseable `ts` (the log writes UTC `...Z` through `boss_review._now`; the tests write offsets; `datetime.fromisoformat` reads both). `test_codex_health.py` pins the field: a `Z` ts, an offset ts, a missing ts, an unparseable ts (None), and file order against `ts` order (the newest in file order wins, as the module does for `last_*`).
- [ ] `codex_blocker.sync` raises only when `last_ts` is None or `last_ts >= C`, where `C` is the newest `cleared=` among the readable `cd` lines inside `## Open blockers` (a line `tracker.scan_marker` and `validate` accept, with a non-empty `cleared`); with no such line, the rule is today's. `cleared=` carries minutes only and a `ts` seconds, so the comparison is against the clear's minute start: a failure in the same minute as the clear counts as new, including one at `HH:MM:00` (one re-raise on the safe side, never a held alert). A clear by `mark_cleared` (the up sync) is such a line too and needs no special case: a new streak's failures are all later. Removing the line from the live tracker leaves nothing to compare, so the blocker is raised again (`boss-tracker archive` only copies stdin into the archive and never edits the live tracker, so it changes nothing by itself); the owner closes a blocker by typing `cleared=<ISO-8601 time with UTC offset>` on the line, for example `cleared=2026-11-12T15:30+01:00`, never a bare `cleared=` (an empty value reads as open: `_classify` at `codex_blocker.py:84`; 20's class c) and not by deleting it. That sentence goes into the SKILL question that 09b writes, not into `codex_blocker.ASK`, whose text cannot hold a `"` (`tracker.py:205-206`). A `cleared=` later than the `now` the sync was given plus 60 seconds (a local time read as UTC, a mistyped month) is ignored as invalid, not capped: it does not hold, the blocker is treated as having no usable clear, and `sync` says so on stderr; one at or before `now` + 60 s is used as typed, so a typo never silences the alert for hours or weeks (Opus round 2, N4). Documented in the module docstring: the concurrent writer that appends an older `ts` after the clear.
