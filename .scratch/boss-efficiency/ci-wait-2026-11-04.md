## Wait until the last job starts

Method: for each repository, runs created since 2026-10-01 with event `pull_request` or `push` and conclusion success or failure; a random sample of up to 40 per cell (seed 1); for each, the latest job `started_at` minus the run's `created_at`, from `actions/runs/<id>/jobs`. "Before" and "after" split at the date a repository's PR matrix went away (render-doc 2026-10-25 16:52 UTC, mail-replies 15:48 UTC, tiroir-clients 17:26 UTC), or at rule P16 (2026-10-22) for repositories that never had a matrix. sheaf, tt-tiroir and claude-boss have no "before" window: their runs start after 10-22.

Pool load: the API gives the state of the runners only now (org runners `t-compute-1..3` for sweatshop-ai, `t-compute-tt-1..5` for thinkingtoo, all busy or idle at the moment of the call), not history. As a stand-in, "load" is the number of other runs of the five t-compute repositories whose `created_at` to `updated_at` span contained this run's creation time. It counts runs, not jobs, includes runs still queued, and misses any other repository on the same machine. Read it as relative, not absolute. It is blank for sheaf and claude-boss, which run on GitHub-hosted runners.

## What the long waits are: tiroir-library-mcp

tiroir-library-mcp never had a matrix: one job per run, and it still waits a p90 of 75 minutes on pull requests and 100 minutes on pushes. The matrix was not its cause. Two things in the data point elsewhere:

- Its load is the highest of the five t-compute repositories (median 5 to 7, p90 16 to 17, against 1 to 4 elsewhere).
- Its workflow runs on every push to every branch (`on: push:` without a branch list) and on pull requests. Of its 179 pushes to branches other than main, 126 share their commit with a pull request run: the same suite runs twice for one commit. The other t-compute repositories use `push: branches: [main]` (mail-replies, tiroir-clients, render-doc) so a branch is run through its pull request only. The workflow comment says this is intended ("a branch without a pull request still shows a result"); it costs about 126 of its 367 runs. This is not my repository to change. Recommendation for Anton: limit `push:` to `branches: [main]` the way mail-replies did, after confirming with its owner that the branch-without-PR case is not wanted. The same file has no nightly.

The API does not say who cancelled a run, so "superseded by a push" (the workflow's `concurrency: cancel-in-progress`) and "cancelled by a worker" (P16 tells workers to cancel their own superseded runs) cannot be split in the six repositories that have a concurrency group, and the superseded column contains both. claude-boss is the exception: its workflow has no `concurrency:` key, so all 17 of its cancelled runs were cancelled by a person or a script, and 11 of them have a newer run on the same ref (worker cancels of superseded runs).

Runs on main are cancelled too, though a run on main already running is not: a concurrency group holds one running and one pending run, and a newer pending run replaces an older pending one. Cancelled pushes to main: render-doc 38 of 39 (all before 2026-10-25 13:00 UTC, none since its per-run groups), tiroir-mail-replies 50 of 53 (22 since 2026-10-31, where "queued main runs collapse to the newest merge" is written down as the design), tt-tiroir 38 of 38 (all since 2026-10-31), tiroir-library-mcp 10 of 88.

The 48 "other" are a lower bound for a manual or timeout cancel: a worker's cancel of a run whose newer run came later than 60 seconds after the cancel would land there too. tiroir-clients has the largest "other" share (19 of 34); 17 of its 19 are pull request runs, which I did not look into.
